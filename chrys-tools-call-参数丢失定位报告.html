Chrys tools/call 参数丢失定位报告

question-tracker MCP 服务端 · 2026-08-19 · 证据基于用户现场 debug.log 原始字节与本地重放

结论（TL;DR）

Chrys 的 MCP 客户端在发起 tools/call 时把 session 参数过滤掉了：src/chrys/service/mcp/owned.py 的 _MCP_FRAMEWORK_DENYLIST（第 57-68 行）把 "session" 列为框架保留字，_prepare_call_kwargs（第 1082-1086 行）在转发前将 denylist 内的键从参数中剔除——即使工具的 inputSchema 明确声明了 session。于是宿主 UI 显示 {"session":"sr-design"}，发到服务端的线上字节却是 "arguments":{}。该过滤对所有带 session 参数的工具、所有 Chrys 环境确定性生效。question-tracker 服务端本地原样重放同一输入可正常建池。

组件角色判定依据
question-tracker MCP 服务端（v2.0.0）被调方排除嫌疑原样重放用户输入即成功建池；131 项自动化测试（含 23 项真 exe stdio 黑盒）全绿
Chrys MCP 客户端（自报 mcp 0.1.0）调用方问题所在debug.log 中两次 tools/call 的 arguments 均为空对象
模型输出参数来源疑似无辜宿主 UI 能显示参数，说明模型已产出参数；丢失发生在 UI 之后、网络之前的客户端内部

1问题现象

用户升级 question-tracker 到最新版后，AI 在 sr-design 流程中调用 create_session 建池，宿主 UI 展示调用了 {"session": "sr-design"}，但 MCP 返回的却是"未携带 session"的选池指引：

  • 宿主 UI 记录：Input: {"session": "sr-design"}（Status: completed，105ms）
  • 实际返回：{"action_required":"select_session","reason":"missing_session","detail":"本次调用未携带问题池名（session），未执行。", …}
  • 同一形态连续出现两次（日志 id=2、id=3），可稳定复现。

2证据链

证据 A · 用户现场 debug.log（2026-08-19 10:53）决定性
10:51:57 [req]  {"method":"initialize","params":{"protocolVersion":"2025-11-25",
                 "clientInfo":{"name":"mcp","version":"0.1.0"}},"jsonrpc":"2.0","id":0}
10:51:57 [req]  {"method":"tools/list","jsonrpc":"2.0","id":1}
                 → 正常：服务端返回 11 个工具的完整 schema

10:53:31 [resp] 选池指引：missing_session（服务端按收到的空对象正确应答）

                 "arguments":{}},"jsonrpc":"2.0","id":3}   ← 第二次，同样丢空

读取方式：debug.log 的 [req] 行是 MCP 服务端从 stdin 收到的原始字节，无任何中间加工。宿主 UI 展示的参数没有到达这里。

输入   {"name":"create_session","arguments":{"session":"sr-design"}}
输出   {"created":true,"pool_location":"…\\sr-design\\state.json"}   ← 建池成功、落盘正确
证据 C · 同一进程内对照收窄范围
同一 Chrys 客户端、同一 MCP 进程内：
  initialize / notifications/initialized / tools/list   → 全部正常
  tools/call                                            → 只有它丢空 arguments

连接、握手、序列化框架均正常，问题被压缩到 Chrys 客户端组装 tools/call 的 params.arguments 这一处。

3根因（代码级实锤）

Chrys 客户端 src/chrys/service/mcp/owned.py 中存在一个框架保留字黑名单：

根因代码 · owned.py:57-68 / 1082-1086决定性的第二份证据
_MCP_FRAMEWORK_DENYLIST: frozenset[str] = frozenset({
    "chat_options", "tools", "tool_choice",
    "session",          ← 被当成框架保留字
    "thread", "conversation_id", "options", "response_format", "_meta",
})

# _prepare_call_kwargs：转发前过滤参数
filtered_kwargs = {
    k: v for k, v in kwargs.items()
    if k != "_meta" and (k in extras or (k in declared and k not in _MCP_FRAMEWORK_DENYLIST))
}                                   # ↑ 即使 inputSchema 声明了 session，也被这行丢弃

链条闭合：add_questions/get_status/create_session 等工具的 schema 都声明了 session 参数 → 模型正确产出 session → 过滤函数以"框架保留字"为由将其剔除 → 线上 arguments:{} → 服务端按"未携带 session"返回选池指引。无参工具（list_sessions 只带 include_archived/project）不受影响，与现场完全吻合。

为什么以前没爆：question-tracker 1.x 时代用 .sdd/.current_session 标记文件路由，不需要 session 参数；2.0 起 session 成为必填参数，黑名单问题随之暴露。黑名单自 2026-06-22 的 c53e8dc0（架构重构提交）起就存在于 Chrys 代码中。

逃生通道未接线：Chrys 代码里预留了白名单参数 additional_tool_argument_names（可放行 denylist 内的键），但它只在内部构造函数传递，没有接入用户配置——终端用户无任何配置手段可绕过。

4影响范围

  • 所有需要参数的 MCP 工具调用均不可达（建池、提问、回答、归档……），无参工具（list_sessions）不受影响；
  • 影响面 = 使用该 Chrys 客户端版本（自报 mcp 0.1.0）的全部 MCP 服务器，不限于 question-tracker。

5给 Chrys 的修复建议

原则：工具 inputSchema 声明优先于框架黑名单——工具既然声明了 session，就必须透传；黑名单只应拦截"工具未声明、被框架/模型夹带"的键。

最小补丁 · owned.py _prepare_call_kwargs建议
 filtered_kwargs = {
     k: v
     for k, v in kwargs.items()
-    if k != "_meta" and (k in extras or (k in declared and k not in _MCP_FRAMEWORK_DENYLIST))
+    if k != "_meta" and (k in declared or (k in extras and k not in _MCP_FRAMEWORK_DENYLIST))
 }
  • 回归测试：注册一个 inputSchema 声明 session 参数的测试 MCP 工具，调用时断言线上 params.arguments 包含 session 原值；另补一个 denylist 键未被声明时仍被拦截的反向用例。
  • 可选：把 additional_tool_argument_names 接入用户配置作为显式逃生通道；修复合入前，受影响用户无配置级绕过手段，只能依赖本补丁。
  • 可观测：参数被过滤时建议日志告警（"参数 session 被框架黑名单过滤"），本次问题若有此日志可提前两周发现。

6服务端已做的兼容与取证能力（供参考）

  • 双重编码自愈：arguments 以字符串形态到达时自动二次解析；
  • 类型异常精确报错：session 为非字符串/null 时返回 invalid_session 并带实际收到值；
  • 现场取证开关：MCP 配置 env 设 QUESTION_TRACKER_DEBUG=1 后，原始请求/响应逐行写入 ~/.question-tracker/debug.log（本次证据即来源于此）。
若 Chrys 修复后仍有个别形态（如参数被多套一层包装）兼容不了，把新的 debug.log 发回，服务端可以再加对应解包兼容——但目前证据不支持预判更多形态。
